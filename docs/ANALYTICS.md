# Domain events and cookieless analytics

URL redirect counters are first-party operational aggregates, independent of DataFast and its feature flags. `/admin/redirects` reports all-time and daily UTC totals for managed rules and public founder redirects, with estimated browser/bot separation. The response schedules an atomic counter update in the background. Migration `0011` adds two tables keyed by known redirect/founder identity and UTC day; no event-per-visit rows or visitor identifiers are retained. Query strings, referrers, IPs and raw user agents are not stored. Legacy account paths use the constant `/profile/[account-id]`. Private profiles, noncanonical hosts, HEAD, prefetch/RSC, DNT/GPC and saved opt-outs are excluded. These counts are best effort request observations, not unique people, verified clicks or financial events. Historical totals begin with this feature; deletion of the corresponding rule/founder cascades to its counters. Daily aggregates are retained with that identity so lifetime totals remain available.

The shared Next configuration enables `skipProxyUrlNormalize` so Proxy can inspect Flight and router-prefetch headers; Next otherwise removes those headers before calling Proxy. The same configuration is copied into the standalone runtime. These headers affect measurement eligibility only, never authorization or the redirect destination.

Browser measurement requires the exact canonical `SITE_URL` origin. A preview hostname serving the same production resource does not initialize browser measurement. Server crawler measurement accepts only the canonical routed Host authority; `Forwarded` and `X-Forwarded-Host` do not authorize preview traffic.

The PostgreSQL `analytics_events` ledger records server-owned business facts. Migration `0006` adds an immutable event ID, unique business key, allowlisted event name, optional site reference, timestamp and bounded property object. The application schema rejects arbitrary properties, raw URLs, email addresses, IP addresses, provider payloads and unknown event names. There is no public arbitrary event insertion endpoint.

Events are inserted in the business transaction where possible: website publication, ownership transfer, performance attempt/result/failure, badge verification/award, ranking closure/weekly entries/results, generated share cards, checkout initiation, confirmed payment/subscription transitions and ad approval. The unique business key makes worker retries idempotent; a rolled-back business transaction leaves no event. A checkout-start event records local initiation, not a completed provider purchase. Payment events come from the verified payment ledger, never the browser return URL.

The role-protected `GET /api/admin/report?section=analytics` backend groups the last thirty days by UTC day and event name. It returns counts, not identifying row data; the focused `/admin` interface does not expose the former analytics section. Advertisement click observations retain their existing origin, quota, active-placement and deduplication checks. Their separate `unverified_interaction` classification is explicitly not proof of a human or a billable click. They never affect rankings, ownership, entitlements or financial totals. Browser pageviews and founder/leaderboard views are not admitted to this trusted business-event ledger.

The official `datafast@3.0.18` npm SDK uses native `cookieless: true`. There is no cookie banner or floating analytics control, and the Google Analytics browser loader is disabled even when its server configuration remains present. This is a technical storage choice, not a claim of blanket legal exemption. DataFast derives a pseudonymous visitor identifier using provider-side signals and a daily rotating salt. Visitor/session IDs and the checkout attribution snapshot stay in tab session storage; the SDK delivery queue can temporarily use browser storage. No persistent visitor cookies, `identify`, client-side `trackPayment`, cross-domain linking or automatic payment detection are used.

Automatic pageview capture is disabled: the application sends explicit public pathnames. Private paths (including account profiles), queries, fragments and sensitive referrers are excluded. Navigation to private paths, queries or fragments uses a fresh document before third-party code can observe the destination. GPC/DNT and saved legacy opt-outs deny collection. The migration removes accessible legacy GA/DataFast cookies and old SDK storage without touching authentication/security cookies. A denied preference remains denied. Changed browser privacy signals stop the SDK and suppress pending account attribution through the existing endpoint. SDK automation filtering remains an estimate, not proof of human identity.

The callback `onCookielessVisitorId` supplies the provider-returned visitor UUID. Only the same tab, canonical origin and UTC day may include this value in validated checkout headers. No visitor ID is read from old cookies. New order snapshots use `analyticsMode: "cookieless"` and `analyticsEligible`; they do not fabricate `analyticsConsent: true`. Previously consented snapshots remain readable, and revocation disables both modes. Attribution never grants entitlement or proves a payment.

Only confirmed Dodo initial checkout payments are sent from the durable outbox, within 24 hours of order creation. Names and emails are excluded. Stable `dodo:<payment_id>` transaction IDs deduplicate provider retries. A return URL is never payment evidence, and later subscription renewals do not reuse old attribution. Daily rotation and the lack of persistent cookies limit cross-day, delayed and multi-touch attribution. Dodo and the application ledger remain authoritative for accounting/refunds. Do not also configure Dodo's direct DataFast webhook: there must be one revenue writer.

`@datafast/ai-crawl@1.0.9` separately measures AI/search crawler requests in `src/proxy.ts`, scheduled using Next's `waitUntil` without delaying the page. It is disabled by default and always disabled in demos. Normal browser traffic is filtered by the official package. Public crawler files such as `robots.txt`, `llms.txt` and sitemaps remain eligible. Private routes, queries, prefetch/RSC requests, DNT/GPC, cookies, authorization and referrer headers are excluded. Proxy mode observes requested URLs, not the final page status. DataFast classifies crawler type and verification confidence; this never affects rankings or trusted application counts.

Set `DATAFAST_BOT_TRUSTED_IP_HEADER` only after the ingress is restricted to a trusted proxy which removes client-supplied copies and overwrites the selected header with one validated client IP. The default `none` sends no client IP: these are unverified crawler observations, not verified crawler identities. They may be hidden by the dashboard's default IP-verified filter; change that filter to inspect them. Comma-separated IP chains are rejected. The optional `DATAFAST_BOT_TOKEN` is a separate server-only `dfbot_` token; it is not the payment API key.

Activation for this site (never reuse IndieTools' website ID):

1. Create a TheFastestWeb website in DataFast with the deployed hostname. Set `DATAFAST_WEBSITE_ID` and `DATAFAST_DOMAIN`; the hostname must match `SITE_URL`.
2. In DataFast website settings enable **Cookieless / privacy mode** (`isCookieless: true` in the website API), matching the SDK. On the production deployment, enable cookieless browser tracking with `ANALYTICS_ENABLED=true`. `DATAFAST_API_KEY` is a website-scoped `df_` key, needed on the web/worker runtime for payment jobs. The existing analytics worker must be running. In `DEPLOYMENT_MODE=demo`, keep both analytics flags `false`; startup validation rejects enabling them.
3. Enable server crawlers separately with `DATAFAST_BOT_TRACKING_ENABLED=true`. Add the optional bot token, deploy it, then enable “Reject unauthenticated requests” in DataFast if desired. Configure trusted IP forwarding only after verifying the proxy boundary.
4. In the DataFast dashboard check a public cookieless visit, the Bot traffic card, and a provider-confirmed initial purchase. Localhost/headless browser SDK traffic is intentionally ignored. This repository's tests mock provider transports; they never send real analytics events.

Both `compose.yaml` and `compose.managed.yaml` pass the analytics flag, public identifiers and payment API key to **web and worker**. Setting them only on web permits pageviews but makes payment delivery skip in the worker. Recreate both processes after changing runtime settings; these values are not build arguments. The crawler flag, bot token and trusted-IP selector belong only to web; the scheduler receives no analytics credentials. `GA_MEASUREMENT_ID` remains available in server configuration for a future explicit integration; it is not exposed by the public analytics config and does not load a browser tracker. Configure DataFast to enable visitor measurement.

No DataFast credentials are bundled. Both analytics flags default to `false`. Enabling a provider without its required website configuration fails startup validation; leaving the payment API key unset skips revenue attribution. See [provider privacy and activation](PROVIDERS.md), [official npm SDK](https://datafa.st/docs/npm), [official crawler SDK](https://datafa.st/docs/bot-traffic-tracking) and [payment API](https://datafa.st/docs/api/website/payments/create).

Synthetic PostgreSQL integration tests verify concurrent deduplication, transactional rollback, bounded report windows and separation of unverified click observations. The tests contact no analytics provider.

Cookieless behavior and attribution limits: [DataFast cookieless documentation](https://datafa.st/docs/gdpr-cookieless-tracking). Provider toggle: [website settings API](https://datafa.st/docs/api/account/websites/update).
