# Email

Microsoft Graph app-only delivery replaces the retired email integration. Typed notification templates, per-category preferences and durable delivery/outbox records sit behind the `EMAIL_ENABLED` gate. Graph acceptance is recorded separately from delivery. Ambiguous sends require reconciliation rather than automatic duplication.

Mailbox permissions, credentials, sender scoping, throttling, uncertainty recovery, signed unsubscribe and template coverage are documented in [Provider operations](PROVIDERS.md#microsoft-graph-email). Authenticated backend APIs retain preferences and notification read state; the former account dashboard UI has been removed.

For rejected Graph requests, worker logs emit `mail.graph_send_failed` with `httpStatus`, `providerCode`, `deliveryCode` and `retryable`, plus the current correlation ID. `providerCode` is a canonical allowlisted machine code, such as `ErrorAccessDenied`, `ErrorSendAsDenied` or `MailboxNotEnabledForRESTAPI`. Unknown codes become `UNRECOGNIZED_ERROR`; missing, malformed, oversized or slow response bodies become `ERROR_DETAILS_UNAVAILABLE`. Diagnostic reads stop at 16 KiB or one second and never log the provider message, raw body, recipient, sender mailbox or token. The error object carries the same safe status/code; durable delivery states retain their existing coarse error classification.

Use these fields to distinguish mailbox/access-policy rejections from authentication and throttling. Successfully acquiring a token with `Mail.Send` does not prove that the selected mailbox allows sending. Check the application consent and Exchange mailbox/application access policies when `ErrorAccessDenied` is reported. Diagnostics never trigger a resend: 401 and 429 retain their existing retry behavior, while timeout, server and transport failures remain uncertain and require review. A 202 means accepted, not delivered. See Microsoft's [Graph error guidance](https://learn.microsoft.com/en-us/graph/errors), [authorization troubleshooting](https://learn.microsoft.com/en-us/graph/resolve-auth-errors) and [sendMail contract](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0).

First verified Google sign-in records one welcome event; returning and concurrent sign-ins preserve the existing identity. Publishing a listing or approving a pending listing records its publication event. Claim issuance records a notification without storing or emailing the ownership proof token. These events commit with their domain transaction. Messages expose only validated site, score, ranking, period and internal destination fields. Rendering remaps links to removed dashboard/claim/competition pages to `/submit`. The inactivity template is available but no inactivity campaign is scheduled without a defined consent and activity policy.
