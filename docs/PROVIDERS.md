# Provider operations

All provider gates default to `false`. Demo mode forbids real checkout sessions, mail delivery, analytics and scheduled monitoring. Storage and screenshots have separate explicit gates and may be configured for a preview. Credentials belong in runtime secrets; they are never build arguments. Production enablement requires account ownership, sender/domain setup, an approved product catalog, and consent/privacy text. Do not reuse another application's credentials without separately granting access to TheFastestWeb.

## Dodo Payments

Set `PAYMENTS_ENABLED`, `DODO_ENVIRONMENT` (`test_mode` first), `DODO_API_KEY`, and `DODO_WEBHOOK_SECRET`. Configure the signed endpoint `/api/webhooks/dodo` for payment, refund, dispute, and subscription events. Configure checkout products in the application's `products` table; no products or prices are invented by migration. Each active product binds a Dodo product ID, fixed base amount in currency minor units, currency, interval, access kind, and optional duration. Provider price, currency, frequency, discounts, and variable pricing are checked before session creation. Tax-inclusive final payment amounts come from Dodo's authoritative payment record rather than a browser field.

`GET /api/payments/catalog` exposes only available public fields. Authenticated same-origin `POST /api/payments/checkout` accepts `{ productKey, siteId?, idempotencyKey }`; the key must be a UUID. Site ownership is checked in the transaction. Session redirects accept only Dodo's hosted HTTPS checkout domains. `GET /api/payments/orders/:id` returns a checkout's status only to its owner. A redirect from checkout does not grant access.

The Dodo SDK currently exposes an idempotency option without configuring its HTTP header. This implementation deliberately disables create retries, inserts the unique local order before the provider call, and reuses its ready session. The first creator is the sole caller. A network failure or crash after creation leaves `creating`/`uncertain`; repeating the request does not produce another session. Review the provider dashboard and local order metadata before manually reconciling an ambiguous order. A definite rejection is `failed`. Never change an uncertain order to retryable without establishing the provider result.

The receiver verifies Standard Webhooks signatures against the exact bounded raw bytes, including timestamp tolerance, before parsing. It persists only sanitized identifiers, event type/time and a payload hash. Customer, billing, card and raw webhook data are excluded. Event insertion and queue outbox insertion are one transaction; acknowledgement follows commit. A repeated event ID is accepted only for the same resource identity. Dodo documents that retry deliveries can contain a refreshed payload, so a changed payload hash alone is not rejected.

The worker retrieves authoritative provider state, binds product/order/quantity, and atomically updates `payment_ledger`, `subscriptions`, `entitlements`, notifications, and `processed_at`. Monotonic event timestamps prevent older deliveries overwriting newer local state. Full refunds and unresolved disputes revoke only the associated Dodo entitlement; legacy grants remain independent. A deleted site retains payment history and cannot receive live site access. Cancel-at-renewal remains active while Dodo reports active; cancelled/expired/failed states revoke that subscription's grant. Partial refunds remain ledger-visible through provider reconciliation but do not revoke the full entitlement automatically.

Sidebar ads require an active inventory row and an owned site. The original $19/month package uses a verified current subscription payment; fixed-duration one-time products remain supported by the backend. Inventory locks and durable reservations prevent overselling. A definite checkout rejection releases the hold; an ambiguous create keeps it for reconciliation. Payment creates inactive pending creative, and an audited administrator approval is required to publish it. Monthly display ends at the paid provider period end; approval does not add a free month. Paid renewals can extend an approved ad, while recoverable subscriptions retain inventory during payment recovery. One-time approval starts its purchased fixed duration. Unpaid manual release requires provider-cancellation evidence; paid reservations require payment/subscription reconciliation. See [Dodo subscription rules](DODO-PAYMENTS.md#advertising-inventory-and-renewals) and [Advertising operations](ADS.md).

## Microsoft Graph email

Set `EMAIL_ENABLED`, `M365_TENANT_ID`, `M365_CLIENT_ID`, `M365_CLIENT_SECRET`, `M365_SENDER` and `EMAIL_UNSUBSCRIBE_SECRET`. Grant Microsoft Graph **application** `Mail.Send` with administrator consent. Restrict the application to the intended mailbox through Exchange application RBAC. The adapter uses client credentials with the `.default` scope, caches the short-lived token in memory and calls the sender-specific `/users/{sender}/sendMail` endpoint. No provider error bodies, access tokens or recipients are logged.

`enqueueNotification({userId,eventKey,type,variables}, transaction?)` joins domain transactions and deduplicates events. All 15 planned template categories are supported. HTML variables are validated/escaped, destinations stay on the canonical site, and queued recipients come from the current user record. Disabled email retains the in-app notification without building a historical send backlog. Delivery checks the latest category preferences; marketing is opt-in. Account and payment messages are transactional.

`202 Accepted` is stored as **accepted**, never delivered. Graph sendMail does not provide an idempotency guarantee. Explicit throttles/auth rejection can retry; `Retry-After` is carried to queue backoff. A network error, timeout, server error after submission, or stale crashed `sending` state becomes **uncertain**, stops automatic retries, and requires mailbox/provider reconciliation. If recording acceptance fails after submission, the next attempt must not resend automatically. Queue operator retry alone cannot bypass an uncertain delivery.

`/api/notifications/preferences` supports authenticated reads and same-origin updates. Signed `/unsubscribe?token=...` links authorize disabling one optional category for one user. GET displays a confirmation; only POST mutates preferences, avoiding automatic unsubscribe by link scanners. Tokens expire after 180 days and contain no email address. `/email-preview` is a development-only template view and returns 404 in production; Resend delivery source code has been removed.

## R2 media

Set `STORAGE_ENABLED`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, and `R2_PRIVATE_BUCKET`. For public listing media also set a **different** `R2_BUCKET` and HTTPS `R2_PUBLIC_BASE_URL`. Give scoped bucket object permissions; keep private bucket public access disabled. A private object never receives a public URL.

The storage adapter validates project-relative object keys, bounds image input to 16 MiB/40 million pixels, rejects SVG/animation during optimization, strips metadata and emits WebP. Optimized output includes dimensions, bytes, SHA-256 and object identity for database metadata. The trusted renderer can retain originals through the bounded private object API. Downloads enforce content type, byte limit and a 15-second whole-stream deadline. Private presigned reads expire within 30–900 seconds. Tenant/project authorization belongs to the screenshot service and must run before calling these primitives.

## Consent and analytics

Browser trackers require the exact canonical `SITE_URL` origin, even when a preview hostname serves the same production resource. Crawler tracking likewise checks the routed Host authority and ignores forwarded-host claims. Preview traffic is therefore excluded independently of provider enablement flags.

Set `ANALYTICS_ENABLED` with reviewed privacy text and enable the website's DataFast `isCookieless` setting. Public runtime configuration contains DataFast identifiers, never API keys. The official npm SDK uses native cookieless mode with automatic capture disabled; explicit public pathnames are measured. The Google Analytics loader is disabled and there is no cookie notification. Private paths, queries, fragments, preview origins and sensitive referrers are excluded. GPC/DNT and prior opt-outs deny collection. Legacy analytics cookies and storage are removed; essential authentication cookies remain. Visitor/session IDs use tab session storage; delivery retries can use the SDK browser queue. Cookieless mode still involves provider-side processing and requires accurate privacy disclosures.

Confirmed server ledger payments alone enqueue DataFast revenue jobs when the current checkout contains a valid cookieless visitor UUID, or an existing order has explicit legacy consent. New cookieless snapshots use separate mode/eligibility fields, never an implied consent grant. The browser sends the current-day, same-origin tab identifier in validated request headers, not a tracking cookie. Revocation clears both eligibility modes and identifiers on pending account snapshots. No customer name/email is sent. Attribution is limited to initial checkout within 24 hours; recurring renewals are not silently linked. `DATAFAST_API_KEY` must be a website-scoped `df_` key. Currency minor units use ISO precision; transaction IDs are stable and provider-deduplicated. HTTP success without a matching transaction receipt is skipped. Accounting and entitlement remain independent of analytics. Cross-day and delayed attribution is less complete without persistent visitor cookies.

Do not configure Dodo's direct DataFast integration in parallel with this outbox. The separate official `@datafast/ai-crawl` server SDK is controlled by `DATAFAST_BOT_TRACKING_ENABLED`, with an optional server-only `DATAFAST_BOT_TOKEN`. It sends sanitized crawler requests in the background. Client IP verification requires an explicitly configured trusted proxy header; all forwarded IP headers are ignored by default. It does not set browser cookies. Detailed activation and capability limits are in [ANALYTICS.md](ANALYTICS.md).

## Verification and rollback

Unit tests exercise raw-body signature/timestamp tampering, price/redirect boundaries, real Sharp conversion, private bucket behavior, Graph response ambiguity, safe templates, signed unsubscribe and privacy/currency rules. PostgreSQL integration tests use migrated synthetic databases and an unprivileged application role with provider transports mocked; no test contacts Dodo, Microsoft Graph, R2 or DataFast.

To stop a provider, set its gate false and redeploy all web/worker/scheduler roles consistently. Preserve provider event/payment/email records and outbox jobs. Investigate failed/uncertain entries by IDs, then reconcile with the owning provider account; do not erase durable records or replay a payment based on a browser return URL. Redis loss is recoverable from the PostgreSQL outbox. Keep provider schema migrations when rolling application code back; additive financial history must not be dropped.
