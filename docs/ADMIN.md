# Administration

`/admin` is the administrator panel. It has seven pages that share one shell (`src/app/admin/layout.tsx`):

| Page | Shows |
| --- | --- |
| `/admin` | Overview: account, website, advertising and revenue totals, 30-day sign-up, submission and revenue charts, score bands, lifecycle counts, newest records, database and Redis status |
| `/admin/users` | Registered users with plan, role, website count, join and activity dates. Search by name or email; filters for Pro, new and staff accounts |
| `/admin/websites` | Registered websites with owner, lifecycle, listing state, plan, badge state, score and test dates. Search, filters, three sort orders and an owner filter |
| `/admin/ads` | Advertised products with placement, status, clicks and paid period, click charts, then the placement inventory and paid creative review |
| `/admin/payments` | Read-only payment ledger, then the Dodo product catalog |
| `/admin/audit` | Active safeguards, staff roles and the audit log |
| `/admin/redirects` | Editable public-path redirects, daily request counts with bot separation, and former founder usernames |

Read models live in `src/modules/admin/dashboard.ts`. They are server-only queries called from server components, so the new pages add no API surface. Each function rechecks the `admin` grant in the database before it reads, lists are paged at 25 rows, search text is escaped before it reaches `ILIKE`, and sort and filter values are closed sets. Account emails leave the module masked (`ce••••@example.com`); search still matches the full address. Avatars are not loaded, so the panel makes no third-party requests. The panel hides the sponsor sidebars and the public footer.

Every page and its metadata call `authorizeAdmin()` (`src/app/admin/authorize.ts`). The layout calls it too, but it is not the boundary: layouts do not re-render on client navigation. `src/proxy.ts` adds `Cache-Control: private, no-store`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer` and same-origin opener and resource policies to `/admin` and `/api/admin`; authorization stays in the handlers. `src/app/admin/page.test.ts` checks the not-found boundary for every page, its metadata and the layout, and `scripts/verify-private.mjs` checks all seven routes.

The panel requires a full administrator before rendering either content or metadata and is excluded from indexing. Anonymous visitors, ordinary accounts and moderators receive not found. The account menu exposes its link only to full administrators. Roles live in `admin_roles`; neither an email address nor an environment allowlist confers privileges. Every report/action rechecks the current database grant, and a revoked role cannot confirm an earlier preview.

The first administrator must first have a normal account. Run the private jobs-container command with its UUID repeated as explicit confirmation:

```sh
node dist/jobs/admin-bootstrap.cjs --user ACCOUNT_UUID --confirm-user ACCOUNT_UUID --reason 'Initial owner-approved administrator assignment'
```

Bootstrap succeeds only when no administrator exists and writes an audit record in the same transaction. It never creates an account or prints its email. Later role changes require a separately authorized database/operator action; no anonymous enrollment endpoint exists.

The payments page shows the two original packages, Dodo environment/configuration status, product bindings and synchronization results. It offers explicit preview/confirmation for creating, verifying or binding products, or updating the permitted details of an app-created product. The packages remain $9 once for lifetime account Pro and $19/month for a sidebar advertisement. Configuration secrets stay in the server environment. Read the complete [Dodo catalog and payment procedure](DODO-PAYMENTS.md) before configuring the merchant account.

The advertisement section configures the five positions on each sidebar and reviews paid creative. Reports use bounded pages and load-more controls. Enabling occupied or reserved capacity is rejected. Approval shows the creative, destination and placement, requires an explicit review checkbox, and rechecks payment, ownership and the valid paid period on the server. An active reservation with pending or inactive creative can be reviewed for recovery; an already published advertisement is excluded from duplicate approval.

All panel mutations require a reason and preview. A five-minute HMAC confirmation binds the actor, exact action and current state; the catalog preview also binds the Dodo environment. Local advertisement changes atomically record before/after evidence and reject replayed confirmations. Remote catalog changes first commit a pending journal entry, then record the provider outcome; an ambiguous creation cannot be repeated automatically. No bulk delete or financial-status override is exposed.

Each row on `/admin/websites` has a primary-category editor using the expanded catalog. Its preview binds the existing normalized assignments and the active destination category. Confirmation replaces the previous primary and obsolete Other assignment, preserves relevant secondary categories, and records both states. Concurrent changes and reused previews are rejected. Website ownership, visibility, lifecycle and measurements remain unchanged. The legacy enum may still contain `other` for newer categories; normalized `site_categories` is authoritative in directory and administrator views.

The backend retains broader administrative reports and actions through `/api/admin/report` and `/api/admin/actions`; the panel pages read through `dashboard.ts` instead, and the advertisement and catalog forms keep using these endpoints. The API still supports its role-restricted directory, ownership, measurement, queue, audit and operational functions. Moderators have only the narrower directory/ownership/measurement permissions defined by the backend. Sensitive bodies, recipient addresses, raw job payloads, claim tokens, checkout URLs and provider secrets are excluded from report projections. Unpaid-hold release remains an API capability requiring provider cancellation evidence; it cannot release a confirmed paid placement.

The original public UI has been restored. Submission and purchase flows use `/submit` and `/pricing`; My Profile uses `/founder/{username}`. Public founder pages publish only explicitly public attribution. The signed-in owner can open an unpublished profile, see its private notice and change its username; generic noindex metadata and other visitors' 404 responses preserve privacy. Google sign-in reserves a persistent private username from the provided display name, never from an email address. Legacy `/profile/{UUID}`, `/founders/{username}` and previous usernames redirect directly to the current canonical address with HTTP 301 when the viewer may access that profile. Reserved old names cannot be claimed by another account. Pricing preserves the original offers, displays compatible active catalog pricing and disables unavailable purchases. A redirect or success query parameter does not grant access.

The redirect editor supports HTTP 301, 302, 307 and 308 for exact public paths on GET/HEAD requests. Administrators preview and confirm each edit; a signed five-minute token binds actor, input and graph state. Confirmation rechecks the database role, serializes concurrent edits, records an audit entry and safely acknowledges an identical retry. Disable a rule to remove it from request handling. External destinations, encoded paths, queries, fragments, chains, cycles and protected account/API/admin routes are rejected; incoming query strings are discarded. Founder aliases are shown for inspection and remain managed by profile ownership, so a general redirect cannot bypass a private profile boundary. See [Founder URLs](FOUNDER-URLS.md) for the migration and reviewed public-name backfill.

Redirect statistics show all-time, today and rolling 30-day counts, last activity and daily charts in UTC. Each managed rule retains its own history across edits; public founder aliases and legacy profile routes are reported separately. Counts begin with migration `0011` and represent eligible GET requests that received a redirect, not unique visitors, verified human clicks or billable events. Browser and detected bot requests are separate estimates. HEAD, prefetch, RSC, private profiles, DNT and GPC are excluded. Collection is best effort after the response; a counter failure cannot block navigation. Daily aggregates store no visitor identifiers, raw user agents, referrers, account IDs in source paths or query strings, and cannot invalidate a pending redirect preview. Only administrators can read the report.

Leaderboard and site-report photos come from the public founder avatar field and render in initial HTML. Failed photos fall back to initials, including failures before hydration. An audited restoration can copy previously published attribution from the original migration snapshot into explicit public founder records; it must match still-public site ownership and preserve every existing founder visibility choice. Current private account names and photos are never used as a public fallback.

Existing authenticated account, founder-collaboration and notification APIs remain available under their original authorization rules. Their former dashboard controls were not restored. Do not infer a present UI from an API's availability or from historical milestone documentation.

PostgreSQL integration tests cover unauthorized role spoofing, single first-admin bootstrap, non-mutating previews, atomic audit, replay prevention, actor/action binding, stale previews, revoked privileges and moderator restrictions. Provider uncertainty, catalog synchronization and monthly advertisement reconciliation are covered separately; see [Dodo Payments](DODO-PAYMENTS.md) and [Provider operations](PROVIDERS.md). Local tests do not establish live merchant readiness.
